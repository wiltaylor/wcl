# Decorators

A decorator is an `@name(...)` annotation attached to a declaration. It is not a comment. Every
decorator has a **schema**, and its arguments are typed and validated. A decorator with no
declaration anywhere in the document is an error.

```console
$ wcl check c.wcl
wcl::eval::schema_violation

  × decorator 'nope' has no @decorator declaration
```

## Where decorators come from

There are three sources, and it matters which one you are looking at.

1. **Built in to the language.** Always in scope, no import. The full list is below.
2. **Declared by you or a library** with `@decorator("name")`. Typed arguments, validated at
   every use site. Most are **inert**: the language parses and checks them, and a consumer
   reads them back. wdoc's `@only` / `@except` and `@wdoc.file` are of this kind.
3. **The two that change the language's own behaviour** — `@contextual` and `@declares_kind`.
   Writing one on a type does not annotate it; it changes how every instance of that type is
   looked up and checked. Treat them as new ground, not as more annotations.

## Argument forms

```wcl
@block("server")                      // one positional
@children("step", min = 2, max = 3)   // positional plus named
@non_empty                            // marker: no arguments at all
@schemaless(annotations = true)       // named only
```

A slot is positional only if its declaration carries `@inline(N)`. Every other slot is
`name = value` at the use site. Validation reports unknown arguments, missing required ones,
surplus positionals, type mismatches and slot-constraint violations, all at the use site.

A decorator may appear **once** per node unless its declaration says otherwise:

```console
  × decorator '@tag' may appear at most once on one node
```

## The built-in vocabulary

Structural — these are the schema language; see [`lang_schemas.md`](lang_schemas.md):

| Decorator | Applies to | Meaning |
| --- | --- | --- |
| `@document(name?)` | type | The document-root schema. Merges per namespace. |
| `@block(name, required_fields?, required_children?, max_children?)` | type | An authorable block kind. |
| `@table(name)` | type | A pipe-table row schema. |
| `@child(kind)` | field | Exactly one nested block of that kind (zero or one if optional). |
| `@children(kind, min?, max?)` | field | A list of nested blocks of that kind. |
| `@inline(slot)` | field | Bind the field to a zero-based positional slot (a block label, or a decorator argument). |
| `@default(value)` | field | The value the field takes when omitted; makes it optional. |
| `@schemaless(reason?, annotations?)` | type, field | Switch validation off for this node. |

Types and values — see [`lang_types.md`](lang_types.md):

| Decorator | Applies to | Meaning |
| --- | --- | --- |
| `@min(value)` | field, alias | Lower bound on a **numeric** value. A non-numeric value is skipped, not rejected. |
| `@max(value)` | field, alias | Upper bound, same rule. |
| `@non_empty` | field, alias | A string or list must not be empty. A list of nothing but `none` counts as empty. |
| `@unit(name, factor)` | type alias | One literal-unit suffix and its factor. Repeatable. |

References and graphs — see [`lang_connections.md`](lang_connections.md):

| Decorator | Applies to | Meaning |
| --- | --- | --- |
| `@ref(kind)` | field | An `identifier` (or `list<identifier>`) that must name an existing block of that kind. |
| `@connections(schema)` | field | Accumulate `a -> b` statements into a list of that connection's records. |
| `@dynamic` | connection | Allow an operand that names no literal block; project it as a raw id. |
| `@by_ref` | type | Instances reify as a resolvable reference rather than an inlined copy. |

Metadata and self-declaration:

| Decorator | Applies to | Meaning |
| --- | --- | --- |
| `@doc(text)` | any declaration | Documentation text that travels with the declaration. |
| `@decorator(name, repeatable?)` | type | Makes the type the argument schema for a `@name` decorator. |
| `@applies_to(on, kinds?)` | decorator schema | Restrict which syntactic positions the decorator is legal in. |

Host-behaviour, covered below:

| Decorator | Applies to | Meaning |
| --- | --- | --- |
| `@contextual(reason?)` | type | Placement decided by context; children generated by the host. |
| `@declares_kind(name?, params, body?)` | type | Instances of the type declare block kinds of their own. |
| `@block_slot` | type | A `slot name: Type` names a nested-block hole, not a scalar parameter. |

### These schemas occupy 23 type names

A real type declaration backs each built-in decorator, injected into the **root** namespace.
Declare a type of your own under one of those names and it fails before evaluation:

```console
$ wcl check t.wcl
wcl::parse

  × duplicate declaration 'Table'
```

The taken names are `AppliesTo`, `Block`, `BlockSlot`, `ByRefDecorator`, `Child`, `Children`,
`Connections`, `Contextual`, `DeclaresKind`, `Decorator`, `DecoratorPosition`, `Default`,
`DocDecorator`, `Document`, `DynamicDecorator`, `Inline`, `MaxDecorator`, `MinDecorator`,
`NonEmptyDecorator`, `RefDecorator`, `Schemaless`, `Table` and `Unit`.

`Table` and `Document` are the two that bite in practice. Rename your type, or declare a
`namespace` — a namespaced `type Table` is fine, because the collision is per namespace.

## `@unit` — literal-unit suffixes

`@unit` is the only repeatable built-in. It goes on a type alias, and each occurrence names one
suffix and its factor. A literal such as `5MiB` then resolves against the declared type of the
field it is assigned to.

```wcl
@unit("B", 1) @unit("KiB", 1024) @unit("MiB", 1048576)
type Size = u64

@document type Doc { size: Size?  label: utf8? }

size  = 5MiB
label = format_unit(size, "Size", "MiB")
```

```console
$ wcl get u.wcl size
5242880u64
$ wcl get u.wcl label
"5 MiB"
```

The three `std.*` unit types (`std.ByteSize`, `std.Distance`, `std.Duration`) are always in
scope with no import.

## Declaring your own

`@decorator("name")` makes a type the argument schema for `@name`. `@inline(N)` slots take
positional arguments; every other slot is named-only.

```wcl
@decorator("range")
@applies_to(on = [:type_field])
type Range {
  @inline(0) min: i64
  @inline(1) max: i64
}

@block("field") type Field {
  @inline(0) id: identifier
  @range(0, 100) score: i64
}
```

`@applies_to(on = […])` restricts the syntactic positions. The vocabulary is
`:field`, `:fn`, `:block`, `:type`, `:interface`, `:type_field`, `:union`, `:variant`,
`:symbol_set`, `:symbol`, `:connection`. Omit it and the decorator is legal anywhere.

```console
$ wcl check b.wcl
wcl::eval::schema_violation

  × decorator '@range' is not applicable in the 'type' position
```

`@decorator("tag", repeatable = true)` allows more than one occurrence per node.

## `@declares_kind` — an instance that declares a kind

`@declares_kind` on a `@block` type says that **instances** of that type declare block kinds of
their own. It is how a host adds a component / widget / macro concept without the language ever
learning that concept's name.

Its arguments name where to find the pieces on the declarer:

| Argument | Meaning |
| --- | --- |
| `name` | Which `@inline(N)` label of the declarer carries the declared kind's name. Defaults to `0`. |
| `params` | The declarer field holding its parameter blocks. Required. |
| `body` | The declarer field holding the template body. The language never reads it — expansion belongs to the host. |

The language derives a `@block` schema from the declarer's params: one field per param, optional
when the param carries a `default`, required otherwise. An instance of the declared kind is then
an ordinary block.

```wcl
// The host declares its component concept once…
@block("component")
@declares_kind(name = 0, params = "slots", body = "body")
type Component {
  @inline(0) name: identifier
  @children("slot") slots: list<Slot>
  @child("body")    body:  ComponentBody
}
@block("slot") type Slot { @inline(0) name: identifier  default: utf8? }
@block("body") @schemaless type ComponentBody { }

@block("panel") type Panel { @inline(0) id: identifier }

@document type Doc {
  @children("component") components: list<Component>
  @children("panel")     panels:     list<Panel>
}

// …and every instance of it declares a new kind.
component metric_card {
  slot label
  slot status { default = "ok" }
  body { }
}

// `metric_card` is now an ordinary block kind.
panel dash {
  metric_card { label = "CPU" }
}
```

Misspell a slot and you get the ordinary errors, named after the *declared* kind:

```console
$ wcl check e.wcl
wcl::eval::schema_violation

  × field 'labl' is not declared by schema 'metric_card'

wcl::eval::schema_violation

  × block 'metric_card' is missing required field 'label'
```

Three consequences to respect:

1. **The derived schemas are built lazily and cached.** Deriving one evaluates the declarer's
   labels and param blocks, so it cannot happen at parse time.
2. **A derived schema is not a declaration.** Kind lookup reaches it, but it does not appear
   among the document's type declarations, because the document never declared it. Anything
   that introspects by walking declarations will not find it.
3. **A collision is an error, not a precedence rule.** Say a `@declares_kind` instance declares
   a kind that a `@block` / `@table` type also declares. Expansion would prefer the declarer
   and schema lookup would prefer the declared type, so instances behave incoherently. The
   collision check therefore looks the kind up **without** the derived-schema fallback, so a
   declared kind cannot collide with itself. It reports the clash as `DeclaredKindCollision`.

Note in the example that `metric_card` is legal inside `panel`, which declares no such child
kind. A derived kind is marked contextual, which is the next decorator.

## `@contextual` — placement decided by context

`@contextual` on a `@block` type says two things:

- The block is legal **wherever nested blocks are allowed at all**. No parent has to list it as
  a child kind. Its body is not validated in place either, because the body only means
  something once expanded with bindings.
- Its children are **generated**. The host registers an *expander* — a callback on the
  `Environment` — that says what a block of that kind expands to. The language consults it when
  it projects a `@children("kind")` slot, so generated blocks land in the slot exactly like
  authored ones.

A decorator can declare *that* a block expands. It cannot carry *how*: that is behaviour, and it
belongs to the host that defined the vocabulary.

```wcl
type Item = utf8
@block("card") type Card { @inline(0) id: identifier  title: utf8 }

@block("repeat") @contextual
type Repeat {
  @schemaless each: list<Item>
  as: symbol
}

@block("deck") type Deck {
  @inline(0) name: identifier
  @children("card") cards: list<Card>
}

@document type Doc { @children("deck") decks: list<Deck> }

deck main {
  card literal { title = "authored" }
  repeat { each = ["one", "two"]  as = :m
    card $"g_${m}" { title = $"generated ${m}" }
  }
}
```

Demanding a `@contextual` block's generated children from a document opened **without** the
host's expander is a hard error naming the kind. Parsing and formatting never demand them, so
`wcl parse` and `wcl fmt` are unaffected; anything that evaluates must open the document with
the host environment.

## Reading decorators back

Decorators are queryable from inside the document, which is how schema-documentation generators
work without a Rust host:

| Builtin | Answers |
| --- | --- |
| `decorator_names(&Decl)` | The decorator names attached to a declaration. |
| `decorator_arg(&Decl, "name", "slot")` | One argument by slot name — positional or named alike — or `none`. |
| `decorators_for_kind("kind")` | References to the decorator schemas legal on that block kind. |
| `decl_info(&Decl)` | Name, kind, doc comment and schema classification of a declaration. |
| `doc_comment(&Decl)` | The `//` run immediately above a declaration. |
| `type_fields(&Decl)` | Field-description records, own fields first then inherited. |
| `ast_string(&Decl)` | The canonical source of the declaration. |

```wcl
@decorator("range") type Range { @inline(0) min: i64  @inline(1) max: i64 }

@block("field") type Field {
  @inline(0) id: identifier
  @range(0, 100) score: i64
}

@document type Doc {
  @children("field") fields: list<Field>
  @schemaless names: list<utf8>?
  @schemaless minv:  i64?
}

field a { score = 50 }

names = decorator_names(Field.score)                  // ["range"]
minv  = decorator_arg(Field.score, "range", "min")    // 0
```

```console
$ wcl get a.wcl names --json
[
  "range"
]
$ wcl get a.wcl minv
0
```

Note the reference form: `Field.score` names the *declaration's* field, not an instance's, and
it is written bare — not as a string.

`@doc("…")` and a plain `//` comment above a declaration are separate channels.
`decorator_arg(x, "doc", "text")` reads the first; `doc_comment(x)` reads the second.

## Declaring one from a Rust host

A host can inject a decorator schema instead of writing it in WCL. It builds the same type a
`@decorator("name")` declaration would, then adds it to the `Environment`:

```rust
use wcl_lang::{
    BuiltinType, DecoratorBuilder, Environment, TypeBuilder, TypeFieldBuilder, TypeRef, Value,
};

let inline = |n: u64| DecoratorBuilder::new(["inline"]).positional(Value::U64(n));

let mut env = Environment::new();
env.add_type(
    TypeBuilder::new(["Range"])
        .decorator(DecoratorBuilder::new(["decorator"]).positional(Value::Utf8("range".into())))
        .field(TypeFieldBuilder::new("min", TypeRef::Builtin(BuiltinType::I64)).decorator(inline(0)))
        .field(TypeFieldBuilder::new("max", TypeRef::Builtin(BuiltinType::I64)).decorator(inline(1)))
        .build(),
);
```

That is the exact equivalent of the WCL declaration above it. The `@inline(N)` decorators are
not optional: without them the slots are named-only, so `@range(0, 100)` fails with
`positional argument 1 for decorator '@range' has no @inline(0) slot in schema 'Range'`.

Three builders, each consuming `self` so calls chain:

| Builder | Methods |
| --- | --- |
| `TypeBuilder` | `new(path)`, `decorator(d)`, `field(f)`, `build()` |
| `TypeFieldBuilder` | `new(name, ty)`, `optional(bool)`, `decorator(d)` |
| `DecoratorBuilder` | `new(path)`, `positional(Value)`, `named(name, Value)` |

Add each finished type with `Environment::add_type`, then open the document with
`Document::open_with(source, name, &env)`. Run `cargo doc` on `wcl_lang` for the exact
signatures.

A host-injected schema behaves exactly like an authored one. The document does not import it,
and it is in scope for every file that environment opens.

## Gotchas

- An undeclared decorator is an error, not an ignored annotation. Importing the library that
  declares it is usually the fix.
- The built-in schemas take 23 root-namespace type names. `type Table` and `type Document` fail
  as `duplicate declaration`.
- A decorator applies to the **next declaration only**.
- Positional arguments exist only where the schema wrote `@inline(N)`. Everything else is
  `name = value`.
- `@contextual` and `@declares_kind` are the two decorators that change the language's
  behaviour. Everything else is data the consumer reads back.
- A `@contextual` block evaluated without the host's expander fails. That is not a bug in your
  document; you opened it with the wrong environment.
